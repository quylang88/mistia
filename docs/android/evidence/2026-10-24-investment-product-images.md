# Slice149 — owned product photos

Baseline `5f2a2c0d`; main version148. This slice is accepted locally under the verification below. APK1–4/RC remains incomplete.

The actual native asset form supports Android Photo Picker and full-resolution camera capture through a private, non-exported FileProvider restricted to `investment-photo-capture/`. Runtime permission failure is recoverable. The form stages a preview, removes photos explicitly and discards unreserved selections on Cancel. Stable owner/asset/form identity prevents an old picker result attaching to a replacement form. A staged identity and the frozen submitted request survive saved-state restoration. Exact retry after an uncertain Room result is enabled only for the same inputs and a valid current proposal; editing the form revokes a captured old retry callback.

Photos become orientation-correct opaque JPEGs with a1600px long edge, at most4,000,000bytes, quality0.9 through0.2 as required by Swift’s actual loop. Thumbnails use240px/quality0.78. Transparent input uses the current app theme’s white or black background, matching Swift `UIColor.systemBackground`. Downloaded full JPEG bytes remain immutable; thumbnail creation does not replace them. Inventory/activity and picker rows use44dp images, selected trade assets34dp, cash history42dp and editor104dp, with rounded clipping and the shipping-box fallback. Actual trade detail also shows the owned photo. Static copy comes from the existing canonical localized catalog.

Private object identities are canonical `ownerUUID/assetUUID/objectUUID.jpg`; the asset stores only that path or explicit null. A dedicated private file cache keeps exact full/thumbnail hashes and an atomic owner manifest. A durable publication revision is reserved before metadata can commit. Late Cancel cannot discard reserved or published bytes. The typed Room boundary checks the actual reservation and files, rereads the full source, applies CAS, verifies protected pending/outbox coherence and commits metadata, outbox and any legacy-unit financial rebuild atomically. The original caller and current owner are checked at the final transaction fence. Ordinary asset save cannot attach an unstaged path. Unknown outcomes retain files; a fresh exact no-write Room proof can recover a lost reply.

Private Storage uses the existing authenticated bucket route with the current JWT/apikey. Every upload/delete checks global&&investment write gates; immutable upload never upserts. HTTP400/409 succeeds only after a private GET proves identical bytes. GET/DELETE404 are handled explicitly, successful bodies are bounded to5MiB and cancellation remains connected through body consumption. Redirects are refused and error messages omit response bodies, tokens and private URLs. A stale session or stale caller cannot deliver a result. All network tests use a controlled HTTPS MockWebServer; no live Supabase request is claimed.

Cache cleanup is revision/path-specific: only locally published photos are pending uploads; previous objects become ready only after upload and the matching asset acknowledgement. An older acknowledgement cannot release a newer replacement. Slice150 must connect these primitives to the real atomic RPC coordinator, including conservative startup reconciliation, upload-before-metadata ordering, current-reference checks at cleanup and ACK/conflict handling. Until that coordinator exists, unknown reserved/orphan files are retained and a restored explicit save can prove its exact outcome. No production cleanup or write occurs in149.
